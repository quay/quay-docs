= Rate limiting and performance configuration fields

[role="_abstract"]
The following configuration fields control rate limiting and performance-related behavior for your {productname} deployment. 

.Rate limiting and performance configuration fields
[cols="3a,1a,2a",options="header"]
|===
| Field | Type | Description 
| **FEATURE_RATE_LIMITS**  | Boolean | Whether to enable rate limits on API and registry endpoints. Setting  FEATURE_RATE_LIMITS to `True` causes `nginx` to limit certain API calls to 30 per second. If that feature is not set, API calls are limited to 300 per second (effectively unlimited). 

**Default:** `False`

| **PROMETHEUS_NAMESPACE** | String | The prefix applied to all exposed Prometheus metrics 

**Default:** `quay`

| **GUNICORN_REGISTRY_TIMEOUT** | Integer | The worker timeout, in seconds, for the `gunicorn-registry` process. Increase this value if workers are terminated during large image pushes or proxy cache blob downloads. The minimum accepted value is `30`. The maximum accepted value is `300`.

**Default:** `300`

| **GUNICORN_WEB_TIMEOUT** | Integer | The worker timeout, in seconds, for the `gunicorn-web` process. Increase this value if workers are terminated during long-running API operations, such as quota queries on large organizations. The minimum accepted value is `30`. The maximum accepted value is `300`.

**Default:** `60`

|===

[IMPORTANT]
====
Increasing the gunicorn worker timeout allows requests to run longer before the worker is forcibly terminated. However, each in-flight request holds CPU and memory resources for the entire duration. Setting very high timeout values can exhaust worker pool resources under concurrent load, potentially degrading performance for all users. Use the minimum value necessary to accommodate your longest expected operations.
====

.Rate limiting and performance example YAML
[source,yaml]
----
# ...
FEATURE_RATE_LIMITS: false
PROMETHEUS_NAMESPACE: quay
GUNICORN_REGISTRY_TIMEOUT: 300
GUNICORN_WEB_TIMEOUT: 60
# ...
----

= Requirements for robot federation

[role="_abstract"]
Before you configure a robot federation entry, confirm that your {productname} deployment can reach the OIDC issuer and that the external tokens meet the requirements for federated token exchange.

== Issuer reachability

To validate an external token, {productname} fetches `<issuer>/.well-known/openid-configuration` and then the `jwks_uri` named in that document. The {productname} pods therefore need network egress to the issuer. On a restricted cluster, allow this through your cluster proxy settings or your egress rules.

The issuer must use `https://`, and its certificate must be one that {productname} trusts. To trust a certificate issued by a private certificate authority, add that authority to the config bundle.

{productname} caches an issuer's discovery document for the lifetime of a worker process and caches its signing keys for one hour.

== Token requirements

An external token presented for exchange must meet the following requirements:

* The token is signed with RS256 or RS384.
* The Token header carries a `kid` key identifier.
* The Token carries `iat` and `exp` claims.
* The `aud` claim of the token includes one of the `audiences` values on the matching federation entry.

== Entry matching

{productname} matches a presented token against federation entries by exact string equality on `issuer` and `subject`. The `issuer` on the entry must equal the token's `iss` claim exactly, including any trailing slash. A mismatched trailing slash is a common cause of an `invalid_grant` response.

A single robot account cannot hold two federation entries with the same `issuer` and `subject`.

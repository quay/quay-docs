= About CCO-based AWS STS authentication for {productname-ocp}

[role="_abstract"]
{productname} {producty} introduces support for the standardized STS configuration flow using the OpenShift Cloud Credential Operator (CCO) and the `CredentialsRequest` API. This integration allows Quay pods on STS-enabled clusters to authenticate to Amazon S3 using short-lived tokens instead of static IAM access keys.

When the `ROLEARN` environment variable is set in the Quay Operator's OLM Subscription, the Operator automatically creates a `CredentialsRequest` resource. CCO then provisions a Secret containing temporary AWS credentials, which the Operator mounts into `quay-app` and `quay-mirror` pods as `AWS_SHARED_CREDENTIALS_FILE`. This eliminates the need to store long-lived IAM user credentials in the `configBundleSecret`.

This approach differs from the existing manual STS configuration in the following ways:

* You do not need to create a static IAM user or generate access keys.
* The Operator manages the `CredentialsRequest` lifecycle automatically. Credentials are refreshed by CCO without operator intervention.
* The Operator monitors credential provisioning status and reports it through `QuayRegistry` status conditions.

.Comparison of STS approaches

[cols="1,1,1",options="header"]
|===
|Attribute |Manual STS (existing) |CCO-based STS (new)

|Credential type
|Static IAM user access key + secret key
|Short-lived tokens provisioned by CCO

|Credential storage
|Stored in `configBundleSecret` (`sts_user_access_key`, `sts_user_secret_key`)
|Mounted automatically from a CCO-provisioned Secret

|Operator involvement
|None — credentials are manually managed
|Operator creates `CredentialsRequest`; CCO manages the lifecycle

|OCP version required
|Any supported OCP version
|OCP 4.14 or later, with STS mode enabled

|Supported platforms
|Standalone, OCP, ROSA
|OCP and ROSA with STS mode enabled

|===

Prerequisites for CCO-based STS include the following:

* Your cluster runs OpenShift 4.14 or later with STS mode enabled (for example, ROSA with STS, or an OCP cluster configured for manual STS mode with CCO).
* CCO is available and not in manual mode without CredentialsRequest support.
* The `objectstorage` component in your `QuayRegistry` CR is set to `managed: false`.
* You have an Amazon S3 bucket already created for Quay object storage.
* You have access to your cluster's OIDC provider URL.

The Operator reports the following status conditions on the `QuayRegistry` CR during CCO-based credential provisioning:

[cols="1,3",options="header"]
|===
|Condition reason |Description

|`CredentialRequestPending`
|The `CredentialsRequest` has been created but CCO has not yet provisioned the credentials Secret. This is a transient state during initial setup or after the role ARN changes.

|`CredentialRequestNotProvisioned`
|CCO did not provision the credentials Secret within the expected time, or the CCO API is not available on this cluster. Check that your cluster has STS mode enabled and that CCO is running.

|`ConflictingCredentials`
|The `ROLEARN` environment variable is set, but static AWS credentials (`s3AccessKey` or `s3SecretKey`) were detected in the `configBundleSecret`. The Operator blocks rollout until the static credentials are removed.

|===

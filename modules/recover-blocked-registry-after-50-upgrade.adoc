= Recover a registry that is already blocked after the {producty} Operator upgrade

[role="_abstract"]
To recover a {productname} registry blocked after a {producty} Operator upgrade by a customized `DATA_MODEL_CACHE_CONFIG` with managed Redis, you can set `cache` to unmanaged on the existing `QuayRegistry` resource. The Operator resumes reconciliation without another Operator upgrade.

.Prerequisites

* The {productname} Operator has already upgraded to {producty}.
* Your `QuayRegistry` remains at a previous version with a cache configuration conflict.
* Your `QuayRegistry` has the `redis` component set to `managed: true`.
* Your config bundle contains a customized `DATA_MODEL_CACHE_CONFIG` field.
* You have reviewed xref:upgrading-cache-component-custom-config[Preparing a custom data model cache configuration before upgrading to {productname} {producty}].

.Procedure

. Confirm the blocked state:
+
[source,terminal]
----
$ oc get quayregistry <example_registry> -n <namespace> -o jsonpath='{.status.currentVersion}{"\n"}{.status.conditions[?(@.type=="RolloutBlocked")]}{"\n"}'
----
+
A blocked registry typically reports a previous `status.currentVersion`, such as `v3.18.2`, with `RolloutBlocked=True`, reason `ConfigInvalid`, and a message that the `cache` component is marked as managed while the config bundle contains required cache fields. The existing registry can remain available while the upgrade is blocked, so availability alone does not indicate a successful upgrade.

. Edit the existing `QuayRegistry` custom resource. Preserve all other component entries and overrides, retain `redis.managed: true`, leave the custom config bundle unchanged, and set only `cache` to `managed: false`.
. Apply the updated `QuayRegistry` resource. The Operator resumes reconciliation automatically. You do not need to reinstall or re-approve the Operator upgrade.
